\section{Prior Work}

There are several recent works that augment large language models with external knowledge sources to achieve better performance on knowledge production tasks. \cite{checkYourFacts} demonstrate that augmenting with external knowledge and self-feedback improves performance on factual knowledge tasks. \cite{llmsZeroShotPlanners} demonstrate that LLMs can produce procedural knowledge, but the VirtualHome environment is limited and the work does not leverage external knowledge except by environment grounding.

\cite{thoughtPropagation} design an analogical prompting process they call Thought Propagation, which asks the model to propose analogous problems, which are each individually solved, and all analogous problems and solutions are included in the prompt to determine the solution to the original problem. \cite{reAct} prompts LLMs to generate a mix of thoughts \textit{and} actions in order to combine the benefits of CoT with the benefits of tool use/retrieval.

\cite{opro} iteratively optimize the prompt by asking LLMs to refine it.

\subsection{multi-agent simulation}

\cite{qian2023communicative} perform software engineering by prompting LLMs to fill various waterfall development roles and allowing them to interact with each other.

\subsection{model-based evaluation}

\cite{prometheus} trains an evaluator model that evaluates generated text as well as GPT-4 (given a rubric) but is open source.

\begin{itemize}
   \item Factual knowledge is most succinctly represented by knowledge graphs, but these graphs leave out contextual information (which is why current approaches to factual generation use retrieved documents instead of KGs).
   \item Procedural knowledge can also be succinctly represented as a graph relating goals with steps, but this also leaves out contextual information.
   \item Retrieving procedural knowledge can be difficult because information is often spread across many more documents.
         \begin{itemize}
            \item To reliably discover the information the model needs, it is already established practice to \href{https://python.langchain.com/docs/modules/data\_connection/retrievers/contextual\_compression/\#embeddingsfilter}{threshhold} retrieved documents based on embedding similarity with the query, or to prompt an LLM to \href{https://python.langchain.com/docs/modules/data\_connection/retrievers/contextual\_compression/\#llmchainfilter}{filter} or \href{https://python.langchain.com/docs/modules/data\_connection/retrievers/contextual\_compression/\#adding-contextual-compression-with-an-llmchainextractor}{compress} the passages.
         \end{itemize}
   \item What is procedural knowledge: does pseudocode count? does instructions to get to the university count? what makes it procedural?
         \begin{itemize}
            \item Procedural knowledge is action knowledge.
            \item Procedural knowledge comes from \textit{motivated} reasoning over factual knowledge.
            \item Humans tend to construct reusable chunks of actions, and recalling and modifying them as needed (see \href{https://en.wikipedia.org/wiki/Procedural_knowledge#Activation}{here}).
         \end{itemize}
   \item What we're doing is different from general summarization because the relevance of individual facts depends on the goal being achieved. It's also different from knowledge extraction because the resulting procedure has to cohesively combine many facts to produce steps, and the end result won't necessarily spell out the underlying facts.
   \item For performance on procedural knowledge, the constraint is procedural reasoning, not fact retrieval. (This is demonstrated by the performance of GPT-4 when just doing retrieval.)
\end{itemize}

\section{LCStep}

\begin{itemize}
   \item talk about procedural knowledge design principles
   \item explain what a good procedure looks like (main idea steps, no unnecessary details, etc.) so others can follow (regardless of the schema they choose for their data)
   \item Our dataset is a procedural knowledge base for using langchain.
   \item The primary task will be procedure generation, and the downstream tasks will be code generation and (as a bonus) code writing Q\&A.
   \item Each procedure also comes with unit tests that check whether generated code accomplishes the procedure.
\end{itemize}

\subsection{API reference}

We generate the API reference material from the source files in the LangChain \href{https://github.com/langchain-ai/langchain/}{GitHub repository} using Sphinx. These files contain descriptions of all APIs in the Python package, including call signatures and argument descriptions. These files do not contain any usage examples or high-level explanation.

\subsection{Conceptual documentation and procedures}

We collect these documents by scraping the \href{https://python.langchain.com/}{LangChain Python docs}. We manually filter out topic pages and stubs, leaving 228 documents. We then manually classified these into around 30 documents of conceptual documentation, and around 180 documents containing tutorials/guides.

For the 180 tutorials/guides, we prompted GPT-4\footnote{See Appendix~\ref{sec:lcstep-formatting} for the full prompt.} to extract a list of high-level steps necessary to accomplish the goal. We then prompted GPT-4\footnote{See Appendix~\ref{sec:lcstep-validation} for the full prompt.} to rate those extracted procedures using a list of criteria. We found that this caught many mistakes where GPT-4 did not follow all the stated instructions. In those cases, we had the model revise the steps to meet the requirements, and then we manually checked the revised versions.

\section{Analogy-augmented generation}

The performance of retrieval-augmented generation (RAG) is highly dependent on the number and size of the documents, as well as the density of relevant information (citation needed). For many tasks, a lot of the knowledge to be retrieved is the same for many queries. In our case, many procedures involving the LangChain library require connecting to a language model, creating a prompt template, and constructing a chain. Instead of collecting this information anew for each similar query, we search over past outputs to find procedures similar to the current query, and then include them in the set of retrieved candidate documents to include in the final prompt.

A good procedural knowledge representation provides context in natural language. This makes the individual parts composable.

\begin{itemize}
   \item \textbf{Bootstrap skills}: We first bootstrap the skill library by asking the model to create a few procedures from the concept documents. This will include simple tasks like ``call an OpenAI language model''.
   \item \textbf{Search skill library}: When we get a new task to generate a procedure for, we first search for related tasks in the skill library to produce a candidate procedure. We then ask the model if any of these are close enough to start working with. We then prompt the model to point out places where the procedure should be different, and mark those with e.g.~(TODO change this to a Cohere model instead of OpenAI).
         \begin{itemize}
            \item \textbf{If nothing similar enough, search docs}: If none were similar, we search over the concept docs \& API reference using regular retrieval, so the model has an idea of what broad steps it needs to take. The prompt might look like ``Here are some documents describing basic actions with LangChain. \{\ldots\} Generate a candidate procedure for the task `\{\ldots\}' based on the conceptual documentation above. If you don't have enough information to fill in the details for a part, write (TODO add more detail) at the beginning of that part''.
         \end{itemize}
   \item \textbf{Iteratively update \& improve}: We now have a candidate procedure, marked with TODOs where things need to be changed or become more specific. We then handle those TODOs one at a time: we create a retrieval query to search the skill library, API ref, and concept docs for that specific step \& TODO. We then provide that info to the model and ask it to modify the procedure to resolve the TODO. We do this until the TODOs are removed.
   \item \textbf{Review \& compare with requirements}: We then allow the model another chance to change the generated procedure by asking it if it meets the requirements we've defined for procedures. This might allow it to go back and make certain sections more specific.
   \item \textbf{Store and return}: We then store the generated procedure in the skill library, and return the procedure as the answer for the how to do the given task.
         \begin{itemize}
            \item When storing, we ask the model to compare the procedure with others in the skill library. If the procedure is relatively distinct, we store it. If not, we ask the model to combine it with the existing one to make it more general. This may involve splitting out steps into sub-goals, which will allow those higher steps to be general (thus reducing the number of different steps in the skill library).
         \end{itemize}
\end{itemize}

This is like storing experience (i.e.~how to do something) instead of facts (i.e.~what something is) in memory. It's also like learning to use tools because we collect a library of ``skills'', but it's different because we don't treat the skills as black boxes: we use them to draw analogies with to solve novel problems.\footnote{See the Wikipedia articles for \href{https://en.wikipedia.org/wiki/Procedural\_knowledge}{procedural knowledge} and \href{https://en.wikipedia.org/wiki/Procedural\_memory}{procedural memory}.} We can call this ``analogy-augmented generation'' (AAG).

grounding stuff:
\begin{itemize}
   \item This approach can still benefit from environment grounding much like Voyager or the two papers cited at the top.
   \item In our case, we ground the output by transforming it into code and then evaluating the code. The first test is whether the code runs; the next is whether the LangChain model/chain/agent produces results that look right to a human or LLM, when compared with the examples from the tutorials.
   \item This method works anywhere real, simulated, or user feedback can be provided. (Component should be generic enough to get feedback from any source. For example, some procedure might need a Cohere model, which we won't have a token for. This will be for a second paper.)
\end{itemize}

To demonstrate that AAG can overcome shortcomings of standard retrieval, we pit the two methods against each other on the task of generating the procedures in LCStep. We also test against a few baselines and oracles which we explain below.  Both methods have access to the API reference and conceptual documentation from the dataset.

\subsection{Baselines}

All prompting methods are performed with \texttt{GPT-4-0614} from OpenAI as well as an instruction-tuned version of LLaMA2.

\begin{itemize}
   \item The \textbf{few-shot} approach will prompt the model with a basic instruction and a few fixed examples of the output format. We expect this method to fail due to a lack of knowledge of LangChain in the models' training data.
   \item The vanilla retrieval-augmented approach (\textbf{RAG}) constructs a prompt by doing retrieval over a vector store containing the conceptual documentation and API reference material.
         \begin{itemize}
            \item We expect to further refine this retrieval process somewhat. This may involve enforcing retrieval diversity by penalizing similarity between retrieved docs, having the model split the query into subqueries to find the individual parts necessary to build the whole answer, or using contextual compression.
            \item This method would also benefit from HyDE \citep{hyde}, I\textsuperscript{3} \citep{i3}, or EAR \citep{ear}. At that point, it might be worth having this optimized version as a separate baseline here.
         \end{itemize}
\end{itemize}

For our experiment, the \textbf{AAG} approach constructs a prompt by retrieval over the same documents as RAG, plus all procedures generated so far. When retrieving from the past outputs, the model is separately presented with the selection prompt as described in Section~\ref{sec:method}.
