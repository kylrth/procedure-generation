# procedure generation

Our current task is recipe generation, based on the RecipeNLG dataset. We will leverage LLMs to do this, with several approaches:

- **zero**: GPT-3.5 prompted zero-shot to generate recipes
- **basic index**: GPT-3.5 with few-shot examples provided by a basic vector store over recipes. We search for recipes similar to the given recipe title, and those similar recipes get placed in the prompt as examples, like in [REPLUG](https://arxiv.org/abs/2301.12652). This means that the reasoning over step-step relationships and step-ingredient relationships is done internally by the LLM in a single pass.
- **HyDE**: simple improvement over the basic index, where instead of searching the index by title we search with whatever (possibly wrong) text the model produces zero-shot, following [Precise Zero-Shot Dense Retrieval without Relevance Labels](https://arxiv.org/abs/2212.10496)
- **chain-of-steps**: The same thing as the basic index, but prompting the model to produce explanations under each step. Explanations for the recipes in the few-shot prompt can be generated by separately asking the LLM to explain the steps of the recipe.
- **chain-of-triplets**: The same thing as chain-of-steps, but the explanation text is a triplet representation of the node and relevant edges, and we’ll do some kind of validation on the graph of these triplets to ensure good step ordering and to check if the procedure links correctly (all ingredients are used, steps are sequential, etc.)
- **custom procedure-aware index**: The index is now a custom graph & vector store of recipes, steps, ingredients, and possibly NER items, instead of a standard index over whole recipes. This is accomplished by thinking of procedures as code: each step is highly precise and dependent on surrounding steps. We want to be able to represent the details of each step as parameters to the general step action (e.g. `bake(cake, 40 minutes)`). Step actions are conditional on each other and the goal, and step details are conditional on the step action and the surrounding details. Each embedded step has edges to previous/following steps, plus edges to the ingredients involved. The text of the steps and ingredients in the output is iteratively refined based on how the neighboring steps & ingredients affect one another. (So the model originally knew that the cake needed to be baked and thus included that step, but now the presence of more eggs than usual in the mixing step can change the bake time for the baking step.)

## evaluation

We will evaluate the generated recipes using the following metrics. Those marked as "model-based" will use an LLM for evaluation:

- **ROUGE**: summarization score using the recipes in the dataset
- **coherence** (model-based): Is the recipe clear and readable according to an LLM?
- **ingredient comparison**: how well the ingredients match with the gold recipe
- **ingredient relevance** (model-based): Does the list of ingredients align with the culinary expectations of the recipe (e.g. no-bake, gluten free, etc.)?
- **ingredient consistency**: Does the ingredients list accurately reflect the exact ingredients and amounts used in the directions?
- **step order** (model-based): Does the order of the steps make sense?
